| 决策项 | 选择 | 说明 |

## 1. 目标拓扑

```text
浏览器
  │  http://<IP>:<port>
  ▼
nginx 容器（唯一入口，同源）
  ├─ /            → 前端 dist 静态资源
  └─ /api/…       → 反代 backend:8080（同源，天然免 CORS）
        │
        ▼
backend 容器（jar，prod profile + 环境变量注入）
  ├─ mysql 容器（+ 数据卷）
  └─ redis 容器（+ 数据卷）

外部依赖：阿里云 OSS（图片存储）、阿里云短信（验证码）、智谱 AI（生成/对话）
```

关键原则：

1. **前后端同源**：nginx 统一入口，前端与 API 同域名，不触发浏览器跨域，无需配置 CORS。
2. **配置全外置**：地址、口令、密钥一律经环境变量注入，`.env` 不进镜像。
3. **生产 fail-fast**：密钥类配置在 prod 下无默认值，缺失直接启动失败，杜绝回退到开发默认值。

## 3. 生产 profile（application-prod.yml）

生产配置与开发默认值分离，通过 `SPRING_PROFILES_ACTIVE=prod` 激活。相对开发额外收敛：

1. 密钥/口令写成**无默认值**占位符：`${JWT_SECRET}`、`${DB_PASSWORD}`、`${REDIS_PASSWORD}`、OSS 密钥、`${MAIL_USERNAME}` / `${MAIL_PASSWORD}`（A-11 邮箱通道）—— 缺失即启动失败。
2. 关闭 MyBatis-Plus 控制台 SQL 打印（`NoLoggingImpl`），不再把 SQL 与用户数据刷屏。
3. 关闭 Swagger / OpenAPI 文档（`springdoc.*.enabled=false`），不对外暴露接口清单。

**已知前置依赖**：prod 下必须有可装配的 `SmsService` 实现（当前 `MockSmsServiceImpl` 为 `@Profile("!prod")`，故 prod 启动会因缺 Bean 失败）——由第 2 步「短信通道可插拔」解决（prod 显式指定 `SMS_PROVIDER=mock`）。

## 7. 第 7 步详设：加固收尾

### 7.1 actuator 健康检查（第 7 步第①项，2026-10-18 详设）

**现状盘点**：

- `backend/pom.xml` 无 `spring-boot-starter-actuator` 依赖；
- `deploy/docker-compose.yml` 中 backend 服务**没有 healthcheck**（仅 mysql/redis 有），nginx `depends_on` 未约束 condition，backend 起没起 nginx 都开始收流量；
- `WebConfig` JWT 拦截器 `addPathPatterns("/**")`，白名单不含 `/actuator/**`——不排除则 health 端点被 401，healthcheck 必失败；
- `eclipse-temurin:17-jre`（Ubuntu jammy）不自带 curl，容器内探 HTTP 需先安装。

**改造清单（共 5 处）**：

| # | 文件 | 改动 |
| --- | --- | --- |
| 1 | `backend/pom.xml` | 新增 `spring-boot-starter-actuator` 依赖 |
| 2 | `backend/src/main/resources/application.yml` | 根级别新增 `management` 配置：web 只暴露 `health`；`show-details: never`（不泄露 redis/db 组件细节）；`management.health.mail.enabled: false`（外部 SMTP 抖动不拖垮健康检查） |
| 3 | `backend/src/main/java/com/housedesign/config/WebConfig.java` | excludePathPatterns 增加 `/actuator/**` |
| 4 | `backend/Dockerfile` | 安装 curl（`apt-get install -y --no-install-recommends curl`） |
| 5 | `deploy/docker-compose.yml` | backend 新增 healthcheck（curl 探 `/actuator/health` 断言 `"status":"UP"`，`start_period` 覆盖 Spring 启动窗口）；nginx `depends_on` 升级为 `condition: service_healthy` |

**安全边界**：`/actuator/health` 仅容器网络内部可达（docker healthcheck 用）；nginx 三分流不转发 `/actuator`，外部访问该路径只会命中 SPA 兜底返回前端页面，actuator 不对外暴露。

**验证标准与记录（2026-10-18，✅ 全过）**：

- [x] 容器内 `curl /actuator/health` 返回 `{"status":"UP"}`（无需 token；prod 容器实测，dev 同用 application.yml 的 management 配置）；
- [x] 响应体不含 redis/db/mail 等组件细节（show-details: never 生效，实测仅 `{"status":"UP"}`）；
- [x] `docker compose up -d --build` 后 `docker compose ps` 显示 backend `(healthy)`，且 nginx 等 `service_healthy` 才启动（启动顺序约束生效）；
- [x] 宿主机 `curl :8080/actuator/health` 返回 HTTP 200 + HTML（SPA 兜底页），actuator JSON 未对外暴露；
- [x] 停 redis 后端点即时转 `{"status":"DOWN"}`，重启 redis 约 35 秒内自愈回 `UP`（容器态转 unhealthy 有 retries=5 防抖，需连续 5 次失败约 75-90 秒，属预期设计）。

**实测补充**：temurin 基础镜像层 `apt-get install curl` 实际命中 "already the newest version"（新版 base 已自带 curl），该 RUN 保留作为 base 镜像变更后的兜底。

### 7.2 优雅停机（第 7 步第②项，2026-10-18 详设）

**现状盘点**：

- 后端无任何 `server.shutdown` / `spring.lifecycle` 配置（grep 零命中），Boot 3.2.5 默认立即停机，SIGTERM 一到就直接掐断在途请求；
- compose 无 `stop_grace_period`——Docker 默认 `StopTimeout=10s`，超时即 SIGKILL。**即使配了优雅停机，不给容器留足时间也是白配**，两者必须成对出现；
- 异步生成任务（单房间最长 12min、整套最长约 30min）不适用优雅停机等待——HTTP 在途请求秒级排空即可，长任务中断由既有 Reconciler + Redis 活跃锁对账置 FAILED 兜底，本步不动该机制。

**改造清单（共 2 处）**：

| # | 文件 | 改动 |
| --- | --- | --- |
| 1 | `backend/src/main/resources/application.yml` | `server.shutdown: graceful` + `spring.lifecycle.timeout-per-shutdown-phase: 30s`（显式声明，不依赖默认值） |
| 2 | `deploy/docker-compose.yml` | backend 服务新增 `stop_grace_period: 45s`（> 30s 排空窗口 + 上下文关闭缓冲；仅 backend，nginx 静态服务无长请求不配） |

**停机时序**：`docker compose stop` → Docker 向 backend 发 SIGTERM → Tomcat 停止接收新连接，最多等 30s 让在途请求完成 → Spring 上下文关闭（连接池、线程池收尾）→ 45s 内进程自然退出；若 45s 仍未退出才 SIGKILL 兜底。

**范围边界（明确不做）**：

- nginx 不配 `stop_grace_period`/`stop_signal`：纯静态文件 + 本地反代，无长请求，SIGTERM 快速退出无感知成本；
- 生成线程池不加 `waitForTasksToCompleteOnShutdown`：分钟级任务不等停机，中断后靠 Reconciler 对账（与本步边界一致，避免为极端场景过度工程）。

**验证标准与记录（2026-10-18，✅ 全过）**：

- [x] `docker inspect --format '{{.Config.StopTimeout}}' deploy-backend-1` 输出 `45`（compose 的 stop_grace_period 映射在 `.Config.StopTimeout`，非 `.HostConfig.StopTimeout`）；
- [x] `docker compose stop backend` 日志完整时序：`Commencing graceful shutdown. Waiting for active requests to complete` → 11ms 后 `Graceful shutdown complete`（无在途请求秒级排空）→ OSS 客户端关闭 → Hikari 连接池 Shutdown initiated/completed；

### 7.3 日志滚动（第 7 步第③项，2026-10-19 详设）

**现状盘点**：

- 后端无 logback 配置，Spring Boot 默认仅控制台输出；容器场景下 stdout 由 Docker json-file 驱动落盘到宿主机；
- 四个服务均无 `logging:` 配置——Docker 默认 json-file **无大小上限**，长期运行日志无限增长，磁盘风险不限于 backend（nginx 访问日志、mysql/redis 自身日志同样写 json-file）。

**方案选型：compose json-file 轮转（放弃 logback 文件日志）**：

| 对比项 | compose json-file 轮转 ✅ | logback 滚动文件 ❌ |
| --- | --- | --- |
| 覆盖面 | 4 个容器一次全兜住 | 仅 backend，nginx/mysql/redis 仍无上限 |
| 改动量 | 纯 compose 配置，零代码 | 新增配置文件 + 需挂数据卷，否则容器重建日志全丢（自欺配置） |
| 适配阶段 | 本机模拟上线正合适 | 真正价值在上集中采集（ELK/Loki），列为上云后升级项 |

**改造清单（1 处）**：

`deploy/docker-compose.yml`：文件顶部新增 `x-logging` YAML 锚点（`json-file` 驱动，单文件上限 10m、保留 3 个），四个服务统一 `logging: *default-logging` 引用——单服务日志上限约 30MB，四容器合计约 120MB 封顶，超限自动滚动覆盖最旧文件。

**验证标准与记录（2026-10-19，✅ 全过）**：

- [x] `docker compose up -d` 重建后，四个容器 `docker inspect … --format '{{.HostConfig.LogConfig.Config}}'` 全部显示 `map[max-file:3 max-size:10m]`；
- [x] `docker compose logs backend --tail 3` 正常可读；
- [x] 重建后 backend 经 healthcheck 转 `(healthy)`，nginx 随后启动，首页 curl 200。

**插曲**：重建时 Docker Desktop 已退出（引擎管道不存在），先启动 Docker Desktop 等引擎就绪（27.5.1）再执行 compose；数据卷持久化未受影响，healthcheck 启动链条完整走通。

**说明**：当前日志量远达不到触发轮转，验证以「配置正确挂载 + 日志可读」为准；真实滚动行为随长期运行自然发生。
