# 筑梦家 · 数据库设计

> 基于 MyBatis-Plus 实体（`com.housedesign.entity`）与 `backend/src/main/resources/db/house_design.sql` 整理，数据库使用 MySQL 8。
> 关联均为**逻辑外键**（实体只存 `Long` 字段，无数据库级外键约束），由应用层保证完整性。
> 建表脚本为 `house_design.sql`（`CREATE TABLE IF NOT EXISTS`）；**已存在的表不会自动加列**，表结构变更需手动执行 ALTER（见 §2 迁移说明）。

> **A-11 变更（2026-10-15）**：新增 `email` 列与唯一索引 `uk_email`，支持邮箱注册与邮箱验证码登录；建表语句在 `db/house_design.sql` 同步修改；存量库执行：

## 8. `t_ai_session` — AI 会话表（A-13）

```sql
CREATE TABLE IF NOT EXISTS `t_ai_session`
(
    `id`              BIGINT      NOT NULL AUTO_INCREMENT COMMENT '主键',
    `user_id`         BIGINT      NOT NULL COMMENT '所属用户（逻辑外键 → t_user.id）',
    `conversation_id` VARCHAR(36) NOT NULL COMMENT '前端会话标识（UUID，与 Redis 记忆键对齐）',
    `title`           VARCHAR(20) NOT NULL DEFAULT '' COMMENT '会话标题（首条用户提问前 20 字）',
    `created_at`      DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `updated_at`      DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '最近活跃时间（列表排序依据）',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_user_conversation` (`user_id`, `conversation_id`)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_unicode_ci COMMENT ='AI 会话表（每用户每会话一行）';
```

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT | PK，自增 | 主键 |
| `user_id` | BIGINT | NOT NULL | 所属用户（逻辑外键 → `t_user.id`） |
| `conversation_id` | VARCHAR(36) | NOT NULL | 前端会话标识（UUID），与 Redis 记忆键 `ai:memory:{userId}:{cid}` 对齐 |
| `title` | VARCHAR(20) | NOT NULL | 会话标题，取首条用户提问前 20 字（对齐前端 TITLE_MAX_LEN） |
| `created_at` / `updated_at` | DATETIME | NOT NULL | 创建 / 最近活跃时间 |

> **唯一约束**：`UNIQUE(user_id, conversation_id)` — 同一会话每用户仅一行，防 IDOR 的查询前提（`WHERE user_id=? AND conversation_id=?`），并发首写由捕获 `DuplicateKeyException` 兜底（沿用注册接口先例）。
> 历史正文**不参与模型记忆**：模型上下文仍走 Redis 30 条窗口，本表只做展示层持久化。

CREATE TABLE IF NOT EXISTS `t_ai_message`

## 10. `t_kb_document` — 知识库文档表

知识库文档的权威元数据，一行代表一份可被检索的文档。文档正文不进本表，正文块见 §11。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT | PK，自增 | 文档 ID |
| `title` | VARCHAR(255) | NOT NULL | 文档标题；不传时取文件名去扩展名 |
| `source_type` | VARCHAR(16) | NOT NULL，默认 `FILE` | `FILE` / `URL` / `TEXT`（枚举 `KbSourceType`） |
| `file_name` | VARCHAR(255) | NULL | 原始文件名 |
| `file_ext` | VARCHAR(16) | NULL | 扩展名，小写不带点 |
| `oss_url` | VARCHAR(512) | NULL | 原文件 OSS 地址 |
| `checksum` | CHAR(64) | NULL，普通索引 | 全文 SHA-256 十六进制，用于文档级去重 |
| `visibility` | VARCHAR(16) | NOT NULL，默认 `PUBLIC` | `PUBLIC` / `PRIVATE`（枚举 `KbVisibility`） |
| `owner_user_id` | BIGINT | NULL | 私有文档归属用户（逻辑外键 → `t_user.id`）；`PUBLIC` 时为 NULL |
| `status` | VARCHAR(16) | NOT NULL，默认 `PENDING`，索引 | 见下方状态机 |
| `error_message` | VARCHAR(1024) | NULL | 失败原因，`FAILED` 时必填 |
| `version` | INT | NOT NULL，默认 1 | 文档版本，重建索引时递增 |
| `chunk_count` | INT | NOT NULL，默认 0 | 当前版本的分块数，`READY` 后回写 |
| `created_at` / `updated_at` | DATETIME | NOT NULL | 创建 / 更新时间 |

> **状态机**：`PENDING`（记录已建，等待入库）→ `PARSING`（解析中）→ `INDEXING`（切块与向量化中）→ `READY`（可检索）/ `FAILED`（失败，写 `error_message`）。
>
> **`version` 不是乐观锁**：它只用于重建索引时区分版本——旧版本分块保留但 `is_active = 0`，便于追溯。实体中**不可**加 `@Version`。

## 11. `t_kb_chunk` — 知识库分块表

分块正文的唯一权威存储，检索命中后取本表内容拼给模型。对应向量写入 PostgreSQL，通过 `chunk_id` 关联（见 §14）。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT | PK，自增 | 分块 ID，同时是 `kb_chunk_vector.chunk_id` |
| `document_id` | BIGINT | NOT NULL | 所属文档（逻辑外键 → `t_kb_document.id`） |
| `version` | INT | NOT NULL | 与 `t_kb_document.version` 对齐 |
| `chunk_no` | INT | NOT NULL | 文档内序号，从 0 开始 |
| `heading` | VARCHAR(255) | NULL | 所属章节标题，用于引用展示与关键词加权 |
| `content` | TEXT | NOT NULL | 分块正文 |
| `content_hash` | CHAR(64) | NOT NULL，索引 | 分块内容 SHA-256，用于块级去重 |
| `token_count` | INT | NOT NULL，默认 0 | 估算 token 数，用于上下文预算控制 |
| `char_count` | INT | NOT NULL，默认 0 | 字符数，便于中文分块参数调优 |
| `is_active` | TINYINT | NOT NULL，默认 1 | 1 = 当前版本参与检索；0 = 历史版本仅追溯 |
| `created_at` | DATETIME | NOT NULL | 创建时间 |

> **唯一键** `uk_doc_ver_chunk (document_id, version, chunk_no)`：同一文档同一版本内分块序号不重复。
>
> **全文索引** `FULLTEXT KEY ft_content (heading, content) WITH PARSER ngram`：为二期混合检索（向量 + 关键词 + RRF 融合）预留，一期纯向量检索不依赖它。

## 12. `t_material` — 材料库表

材料价格与规格。**刻意不放进知识库做向量化**：价格是精确数字，必须整行命中；语义检索只会返回"差不多"的价格，是错误的来源。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT | PK，自增 | 主键 |
| `name` | VARCHAR(128) | NOT NULL | 材料名称，如「强化复合地板 橡木纹」 |
| `category` | VARCHAR(32) | NOT NULL，索引 | `FLOOR` / `WALL` / `BOARD` / `PAINT` / `HARDWARE` / `LIGHT` / `SANITARY` |
| `spec` | VARCHAR(128) | NULL | 规格，如「1220×2440×18mm」 |
| `unit` | VARCHAR(16) | NOT NULL | 计价单位：`㎡` / `m` / `片` / `套` |
| `unit_price` | DECIMAL(10,2) | NOT NULL | 参考单价（元，含税） |
| `brand` | VARCHAR(64) | NULL | 品牌 |
| `eco_level` | VARCHAR(16) | NULL | `E1` / `E0` / `ENF`，仅板材类有效 |
| `style_tags` | VARCHAR(255) | NULL | 适配风格，逗号分隔，如「北欧,日式」 |
| `remark` | VARCHAR(512) | NULL | 备注：施工注意、适用场景 |
| `is_active` | TINYINT | NOT NULL，默认 1 | 1 = 可选用；0 = 已下架 |
| `created_at` / `updated_at` | DATETIME | NOT NULL | 创建 / 更新时间 |

> 尚无实体类。二期 Agent 工具（查价/选材）落地时补 `Material` 实体。

## 13. `t_price_rule` — 计价规则表

施工工序的人工与辅料单价，报价工具按 `code` 精确取用。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT | PK，自增 | 主键 |
| `code` | VARCHAR(64) | NOT NULL | 规则编码，工具按此精确匹配 |
| `name` | VARCHAR(128) | NOT NULL | 规则名称，如「墙面乳胶漆（含腻子）」 |
| `work_type` | VARCHAR(32) | NOT NULL，索引 | `DEMOLITION` / `PLUMBING` / `ELECTRIC` / `TILE` / `CARPENTRY` / `PAINT` / `INSTALL` / `DESIGN` |
| `calc_type` | VARCHAR(16) | NOT NULL | `AREA` 按面积 / `LENGTH` 按长度 / `QUANTITY` 按件 / `FIXED` 一口价 |
| `unit` | VARCHAR(16) | NOT NULL | 计价单位：`㎡` / `m` / `件` / `项` |
| `unit_price` | DECIMAL(10,2) | NOT NULL | 单价（元） |
| `price_tier` | VARCHAR(16) | NOT NULL，默认 `STANDARD` | `BASIC` 基础 / `STANDARD` 中档 / `PREMIUM` 高档 |
| `min_charge` | DECIMAL(10,2) | NULL | 最低收费，小面积时按此兜底 |
| `remark` | VARCHAR(512) | NULL | 备注：包含范围、不含项 |
| `is_active` | TINYINT | NOT NULL，默认 1 | 1 = 启用；0 = 停用 |
| `created_at` / `updated_at` | DATETIME | NOT NULL | 创建 / 更新时间 |

> **唯一键** `uk_code_tier (code, price_tier)`：同一条规则在每个价位档次下只有一行。
>
> **三档设计的用途**：用户预算描述通常是模糊的（"别太夸张"），三档单价让报价工具输出**区间**而不是单点——基础档到高档档即为价格区间。

## 14. `kb_chunk_vector` — 分块向量表（PostgreSQL）

> **不在 MySQL 库内**。该表位于独立的 PostgreSQL 实例（`pgvector/pgvector:pg16` 镜像），库名 `kb_vector`，通过 `PgVectorConfig` 提供的第二数据源访问。
> 与 `t_kb_chunk` 通过 `chunk_id` 逻辑关联，**不做跨库外键**，由应用层保证一致性。
> 建表脚本为 `backend/src/main/resources/db/kb_vector.sql`。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `chunk_id` | BIGINT | PK | 对应 `t_kb_chunk.id` |
| `document_id` | BIGINT | NOT NULL | 冗余文档 ID，用于按文档过滤与删除 |
| `version` | INT | NOT NULL | 冗余文档版本 |
| `embedding` | vector(1024) | NOT NULL | 文本向量，维度与 Embedding 模型对齐（百炼 1024 维） |
| `model` | VARCHAR(64) | NOT NULL | 生成该向量的模型名，便于换模型时识别 |
| `created_at` | TIMESTAMPTZ | NOT NULL，默认 `now()` | 创建时间 |

> **索引**：`idx_kb_vec_doc (document_id, version)` 支持按文档过滤；`idx_kb_vec_hnsw USING hnsw (embedding vector_cosine_ops)` 为余弦距离的 HNSW 近似最近邻索引。
>
> **维度变更代价**：`vector(1024)` 与 Embedding 模型强绑定。更换为不同维度的模型必须重建整张表的向量列，不能只改配置。

## 设计特征与注意事项

1. **全部为逻辑外键，无数据库级外键约束**  
   实体只存 `userId` / `projectId` / `postId` 等 `Long` 字段，未使用外键约束（MyBatis-Plus 实体，非 JPA `@ManyToOne`）。数据库不会阻止脏数据，完整性由应用层（`UserContext.getUserId()` 归属校验）保证。  
   → 风险：删除用户后，其名下项目 / 帖子会成为孤儿数据；删除项目不会级联清理生成记录与社区引用。

2. **冗余计数器**  
   `t_post.like_count` / `comment_count` 为列表页避免 `COUNT(*)` 而设，需与 `t_post_like` / `t_post_comment` 的真实数量保持同步（写入路径上用事务保证），否则会出现计数不一致。

3. **`images` 列为 JSON 字符串**  
   存图片 URL 列表的 JSON 字符串（MyBatis-Plus 侧用 TypeHandler 或手动序列化在 `List<String>` 与 TEXT 间转换），无法用 SQL 直接查询筛选单张图片。

4. **`scene_config` 为 LONGTEXT**  
   photo-tour v2 存整套漫游 JSON（房间数组，每房间含效果图 URL/bbox/热点），不建 `t_generation_room` 子表：房间随任务一次生成、整体 SUCCESS/FAILED、无单房间更新需求；JSON 由后端组装校验后整体写入，数据量大时明显撑大表体积。若未来支持单房间重生成，再拆子表。

5. **`status` 用字符串枚举存储**  
   存 `PENDING` 等字面量，可读性好且新增枚举值安全；代码侧用 `GenerationStatus` 枚举常量对应（MyBatis-Plus 枚举映射）。

6. **`style` 与 `style_label` 双字段**  
   `style` 存用户自由文本（长度可能较长，故 VARCHAR(512)），`style_label` 存枚举 code（VARCHAR(32)），二者**至少填一个**，由应用层校验；`style_label` 便于聚合统计"哪种风格最受欢迎"。

7. **帖子与评论点赞分离**  
   帖子点赞在 `t_post_like`、评论点赞在 `t_comment_like`，互不干扰；两者均以 `UNIQUE(目标id, user_id)` 防重复，配合切换式接口实现"赞/取消赞"。

8. **评论两级结构**  
   `t_post_comment.parent_id` 实现楼中楼：NULL 为顶层评论，非 NULL 为回复（`post_id` 沿用父评论所属帖子）；删除帖子时按 `post_id` 级联删除评论与两种点赞（应用层事务保证）。

9. **跨库拆分：MySQL 存正文、PostgreSQL 存向量**  
   分块正文保留在 MySQL 的 `t_kb_chunk`，向量写入 PostgreSQL 的 `kb_chunk_vector`，二者靠 `chunk_id` 关联。  
   → 原因：pgvector 的 `vector` 类型与 HNSW 索引在 MySQL 侧没有对等能力；而正文放在 PG 会让全文检索、事务与现有业务表割裂。  
   → 代价：写向量与写正文不在同一事务内，只能保证最终一致——删除文档或重建索引时，必须**先**清理 PG 向量**再**更新 MySQL 状态，失败后由重试或对账补偿。  
   → 装配前提：主数据源加 `@Primary`，否则引入第二个 `DataSource` 后 MyBatis-Plus 自动配置会因 `@ConditionalOnSingleCandidate` 不满足而失效。

10. **知识库表与业务表无外键关联**  
   `t_kb_document.owner_user_id` 为逻辑外键；`PUBLIC` 文档该列为 NULL。检索时按 `visibility = 'PUBLIC' OR owner_user_id = 当前用户` 过滤，越权由应用层保证，与全库"逻辑外键"策略一致。

设计说明：

1. **不建 MySQL 表**：计数 10 分钟后自动失效，落库需要定时任务清理且写压力大，Redis 天然适配。
2. **固定窗口**：只在第 1 次失败时设置 TTL，第 2～5 次失败不续期，锁定时长可预期。
3. **计数不持久化**：Redis 重启后计数清零、账号自动解锁（简历项目可接受的权衡，接口文档 §9 已注明）；生产可开 AOF/RDB 或改用持久化限流器。
4. **后续扩展**：注册防刷（A-7）新增 `register:fail:{ip}`，同模式或升级滑动窗口（ZSET）。
5. **验证码双 key 分工**：验证码本体与频控标记拆成两个 key——`*:code` 管"验证码 5 分钟生命周期"，`*:limit` 管"60 秒发送间隔"，TTL 独立互不影响（若只用一个 key，无法表达"验证码还有效但已允许重发"）。
6. **验证码一次性**：校验通过立即 `DEL email:code:login:{email}`，防止同一码被重放；但**校验失败不删**，避免用户输错一位就必须重新获取。错误尝试计数 `email:fail:login:{email}` 已实现（5 次锁定 300s，见登录限流）；**每日发送总量 key `email:daily:email/ip` 用于资损防护**。
7. **黑名单存 token 哈希而非原文（✅ 已实现）**：key 中放 `SHA-256(token)` 十六进制串——JWT payload 含 userId/username，避免令牌明文落 Redis；SHA-256 定长 64 位十六进制字符，key 体积可控且不可逆推。校验时对请求 token 现场哈希后 `EXISTS`。
8. **TTL 精确对齐 token 过期时间**：黑名单只需在 token 自然过期前存在，到期自动清除，不产生长期垃圾数据；这也意味着登出接口只影响"当前这一枚 token"，多端登录的其他 token 不受影响（本期单端使用，可接受；如需"全端登出"后续可改为按 userId 维护版本号/白名单方案）。
9. **AI 记忆两层架构（✅ 已实现，AI-3）**：`MessageWindowChatMemory` 只持有 id 不缓存消息，每轮经 `RedisChatMemoryStore` 实时读写——读 = `GET` + JSON 反序列化（key 不存在返回空列表），写 = 整列表 `SET` 并刷新 TTL。整列表覆盖而非增量追加：窗口淘汰逻辑（保留 10 条）由 ChatMemory 统一裁决，Store 不做业务判断。序列化复用 LangChain4j core 的 `ChatMessageSerializer`（Jackson，支持各消息类型多态），不自写 JSON 结构。
10. **AI 记忆滑动过期**：每次写回都重置 24h TTL——活跃会话持续续命，沉默会话自动回收，无需定时清理；SystemMessage 不入此 key（每轮方法级注入），避免人设修改后旧缓存残留。
