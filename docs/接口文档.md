## 1. 通用约定

### 1.1 鉴权

除 `POST /api/auth/register`、`POST /api/auth/login`、`POST /api/auth/sms/code`、`POST /api/auth/sms/login` 外，所有 `/api/**` 接口需在请求头携带 JWT：

```
Authorization: Bearer <token>
```

- Token 由登录/注册接口返回，有效期默认 7 天（`app.jwt.expiration-ms`）。
- 鉴权失败（缺失/无效/过期）返回 `401`，前端自动登出并跳转登录页。
- 用户主动退出登录（§2.5）后，当前 token 会被写入 **Redis 黑名单**立即失效；此后携带该 token 的请求一律 `401`，无需等 7 天自然过期。黑名单 key 的 TTL 与 token 剩余有效期一致，到期自动清理，无需维护。

### 1.2 统一响应结构

所有接口返回统一包装：

```json
{
  "code": 200,
  "message": "success",
  "data": { }
}
```

- `code`：业务码，`200` 表示成功；非 200 表示失败。
- `message`：提示信息，失败时含具体原因。
- `data`：业务数据，失败时通常为 `null`。

前端取数逻辑：拦截器在 `code !== 200` 时 `ElMessage.error(message)` 并 `reject`。

### 1.3 错误码

| code | 说明                                                                   |
| ---- | -------------------------------------------------------------------- |
| 200  | 成功                                                                   |
| 400  | 参数校验失败 / 上传文件过大                                                      |
| 401  | 未登录或 Token 无效（拦截器层与业务层均有）                                            |
| 404  | 业务资源不存在（如生成任务不存在，由 `BusinessException(404, ...)` 抛出）                 |
| 429  | 登录失败次数过多账号临时锁定（见 §2.2）；短信验证码 60 秒内重复发送（见 §2.6，均为 Redis 频控）      |
| 500  | 服务器内部错误（系统异常）                                                        |
| 503  | AI 服务暂时不可用（模型限流 429 / 超时 / 上游 5xx，见 §11）                            |
| 其他   | `BusinessException` 可携带自定义 code（如智谱额度/Key 错误会在 `errorMessage` 文本中说明） |

### 1.4 上传

文件上传接口使用 `multipart/form-data`，字段名见各接口定义。

### 2.2 登录

`POST /api/auth/login`

**请求体**（JSON）：

```json
{ "username": "zhangsan", "password": "123456" }
```

**响应** `data`：`String`（JWT token）

```json
"eyJhbGciOiJIUzI1NiJ9..."
```

**登录失败限流（✅ 已实现，对应需求文档 S-3 登录部分）**：基于 Redis 失败计数，防止暴力破解（`LoginRateLimiter` + `LoginServiceImpl`，需本地运行 Redis）。

- 同一 `username` 连续登录失败累计 **5 次**后，该账号锁定 **10 分钟**；锁定期间不再校验账号密码，直接拒绝
- 计数 key：`login:fail:{username}`——失败 `INCR`（仅首次失败 `EXPIRE 600s`，固定窗口不续期），登录成功 `DEL` 清零
- 第 1～4 次失败：返回 `400`「用户名或密码错误」（提示口径不变，防用户名枚举）
- 第 5 次失败及锁定期内：返回业务码 `429`，`message` 携带剩余锁定时间
- 失败次数阈值与锁定时长可配置（`app.login-limit.max-fail-count` / `app.login-limit.lock-seconds`）
- 前端无需改造：`request.js` 对 `code !== 200` 统一 `ElMessage.error(message)`，锁定文案直接弹出

锁定响应示例（HTTP 200，业务码在响应体 `code` 中）：

```json
{
  "code": 429,
  "message": "登录失败次数过多，账号已锁定，请于 9 分钟后重试",
  "data": null
}
```

### 2.5 退出登录 ⬜ 规划中（对应需求 A-9 / S-4）

`POST /api/auth/logout` （**需鉴权**，携带当前有效 token）

> 纯前端删除 token 无法让已签发的 JWT 失效——token 在 7 天过期前被窃取仍可冒用。因此退出登录采用**服务端 Redis 黑名单**方案：登出时把当前 token 拉黑，拦截器后续一律拒绝，实现"立即失效"。

**请求头**：

```
Authorization: Bearer <token>
```

**请求体**：无。

**响应** `data`：`null`

```json
{ "code": 200, "message": "success", "data": null }
```

**服务端处理流程**：

1. 拦截器按常规流程验签、验过期、**查黑名单**（黑名单校验逻辑对所有受保护接口生效）；
2. Controller 取出当前 token，计算 `SHA-256(token)`，写入 Redis：key 为 `jwt:blacklist:{sha256(token)}`，TTL = **token 剩余有效期**（`exp - now`，最长 7 天），到期 Redis 自动删除，无需定时清理；
3. 返回成功。拉黑只认 token 本身，与用户后续是否重新登录无关（重新登录拿到的是新 token，不受影响）。

**边界与约定**：

| 场景 | 行为 |
| --- | --- |
| 携带有效 token 正常登出 | 200；该 token 立即失效 |
| 未携带 / 非法 / 已过期 token 调登出 | 拦截器直接 `401`「登录已过期，请重新登录」（前端仍清除本地登录态，见下） |
| 登出后旧 token 再次访问任意受保护接口 | `401`「登录已过期，请重新登录」 |
| 重复点击退出登录 | 首次 200；其后请求因 token 已在黑名单被拦截器拒为 401，前端不依赖重复调用成功 |
| Redis 不可用 | 登出接口返回错误（与登录限流同属 Redis 强依赖，见 README「Redis」小节）；前端**无论接口成败都清除本地 token**，保证用户侧退出闭环 |

> **前端约定**：`useUserStore.logout()` 改为异步——先尝试调用本接口（异常吞掉不弹错），无论成功失败都清空 Pinia 中的 `token`/`userInfo` 与 `localStorage`，再跳转登录页。黑名单只影响服务端校验，不改变前端清理动作。
> **后续复用**：A-5 修改密码实现后，"改密使旧 token 失效"复用同一黑名单机制，无需另建体系。

### 2.6 发送短信验证码（手机登录）✅ 已实现（对应需求 A-10）

`POST /api/auth/sms/code`（无需鉴权，加入 WebConfig 放行列表）

**请求体**（JSON）：

```json
{ "phone": "13800138000" }
```

- `phone` 必填，11 位大陆手机号，正则 `^1[3-9]\d{9}$`

**响应** `data`：`null`

**服务端处理流程**：

1. 校验手机号格式，非法 → `400`「手机号格式不正确」；
2. 发送频控：`GET sms:limit:{phone}`，key 存在 → `429`「发送过于频繁，请 N 秒后再试」（N 取该 key 剩余 TTL）；
3. 生成 6 位随机数字验证码；
4. `SET sms:code:{phone} = 验证码`，TTL **300s**（重发时覆盖旧码并重置 TTL）；
5. `SET sms:limit:{phone} = "1"`，TTL **60s**；
6. 调用 `SmsService` 发送。本期为 Mock 实现：验证码只打印后端日志，**不随响应返回**。

**边界与约定**：

| 场景 | 行为 |
| --- | --- |
| 正常发送 | `200`，`data=null`；后端日志可见验证码 |
| 60s 内重复发送 | `429`，`message` 带剩余秒数 |
| 手机号格式非法 / 为空 | `400` |
| 间隔超过 60s 后再次发送 | `200`；旧验证码被覆盖、TTL 重置为 300s |
| Redis 不可用 | 接口报错（Redis 强依赖，同登录限流，见 §9） |

### 2.7 手机号验证码登录 ✅ 已实现（对应需求 A-10）

`POST /api/auth/sms/login`（无需鉴权，加入 WebConfig 放行列表）

**请求体**（JSON）：

```json
{ "phone": "13800138000", "code": "483920" }
```

- `phone` 必填，11 位手机号；`code` 必填，6 位数字

**响应** `data`：`String`（JWT token，格式与 §2.2 账号登录完全一致）

```json
"eyJhbGciOiJIUzI1NiJ9..."
```

**服务端处理流程**：

1. `GET sms:code:{phone}`：key 不存在或值与入参不一致 → `400`「验证码错误或已过期」（统一口径，不区分原因）；验证码错误时**不删除 key**，允许有效期内重试；
2. 校验通过 → `DEL sms:code:{phone}`（一次性，防同码重放）；
3. 按 `phone` 查询 `t_user`：
   - 已存在 → 直接登录；
   - 不存在 → **自动新建用户**：`phone`=手机号、`username`=手机号、`password`=`NULL`、`nickname` 按现有规则随机生成（「筑梦家er_xxxxxx」）；
4. `jwtUtil.createToken` 签发 JWT 返回。

**边界与约定**：

| 场景 | 行为 |
| --- | --- |
| 验证码正确、用户已存在 | `200` + token |
| 验证码正确、用户不存在 | `200` + token；自动建档 |
| 验证码错误 / 已过期 / 未发送 | `400`「验证码错误或已过期」 |
| 同一验证码提交第二次 | `400`（首次成功即删除） |
| 参数格式非法（手机号/验证码） | `400` |
| Redis 不可用 | 接口报错（Redis 强依赖） |

**安全与后续加固（不在本期）**：

- 验证码错误尝试次数上限（如 5 次）：新增 `sms:try:{phone}` 计数，超限删除验证码——6 位数字存在被枚举的理论空间；
- 同手机号 / 同 IP **每日发送总量上限**：接入真实短信前必做，防止短信接口被刷产生资损；
- 真实短信通道：`SmsService` 接口与 Mock 实现已就位，替换为阿里云/腾讯云实现即可，**接口契约不变**。

## 4. 3D 生成接口 `/api`（生成任务）✅ 已实现（后端）

### 4.1 发起生成

`POST /api/projects/{projectId}/generate` （需鉴权）

**说明**：校验项目归属与是否存在设计图 → 创建 `PENDING` 任务落库 → 异步线程池处理（状态流转 `PENDING → PROCESSING → SUCCESS/FAILED`）。调用后立即返回任务信息，前端需轮询状态。

**AI 提示词组装流程**：
1. 从 `t_design_project.style_label` 取预设 code（若有）；`style` 为用户自定义要求（若有）
2. 有 `style_label` 时 `DesignStyle.fromCode(code)` 反查枚举，拿到 `label` 和 `prompt` 字段
3. 拼装 AI 请求（智谱）：预设风格 prompt + 用户自定义要求文本
   示例：`"请生成一套房屋室内装修效果图，风格为：现代简约。设计要求：中性灰白、干净直线、哑光材质、隐形把手、无主灯设计。用户补充要求：原木色、温馨、多绿植。画面写实、光线自然、符合装修效果图规范"`
4. 调用智谱 CogView（`POST /images/generations` 发起 → `GET /async-result/{task_id}` 轮询）异步生成，生成图下载落盘到本地 `storage/designs/` 后，将本地 URL 写入 `panoramaUrl`，结果落 `t_generated_model`

> 前端只需传 `styleLabel` code（见 §3.1 风格枚举表），**永远不直接传 prompt**，避免 prompt 注入；`style` 自由文本由后端拼装进固定模板，同样经长度/敏感词校验。

**响应** `data`：`GenerationResponse`

```json
{
  "id": 100,
  "projectId": 10,
  "status": "PENDING",
  "provider": null,
  "modelUrl": null,
  "previewImageUrl": null,
  "panoramaUrl": null,
  "sceneConfig": null,
  "errorMessage": null,
  "createdAt": "2026-07-13T10:01:00",
  "updatedAt": "2026-07-13T10:01:00"
}
```

## 9. 关键状态码 / 异常场景速查

| 场景                   | HTTP / code                              | 处理建议                           |
| -------------------- | ---------------------------------------- | ------------------------------ |
| 未带 Token 访问受保护接口     | 401                                      | 重新登录                           |
| 退出登录后旧 token 再访问     | 401（token 已命中 Redis 黑名单，见 §2.5）           | 重新登录；黑名单 TTL 到期自动清除            |
| 智谱 `429` 限流（短时）      | 任务 `FAILED`，`errorMessage` 含"限流…重试"      | 等待后重新点生成（后端已对 429/5xx 做指数退避重试） |
| 智谱额度耗尽（持续 429 / 402） | 任务 `FAILED`，`errorMessage` 含"额度不足/充值"    | 到 open.bigmodel.cn 充值          |
| 智谱 `401/403`         | 任务 `FAILED`，`errorMessage` 含"API Key 无效" | 检查 `app.ai.api-key`            |
| 上传文件过大               | 400 "上传文件过大"                             | 压缩后重试                          |
| 参数校验失败（如用户名过短）       | 400 + 具体 message                         | 按提示修正入参                        |
| AI 对话模型限流 / 超时 / 上游故障 | 503「对不起，当前AI服务繁忙，请稍后再试~」（见 §11）        | 稍后重试；Key 错误/欠费（401）不转 503，原样暴露便于排查 |
| 同一账号连续登录失败 ≥ 5 次    | 业务码 429，message 含剩余锁定分钟数（见 §2.2）        | 10 分钟后重试；计数存 Redis，重启 Redis 即清空 |

## 10. 未来扩展：AI 风格预优化（暂不实现）

> 当前已支持 `styleLabel`（预设 code）+ `style`（自由文本）双输入（§3.1）。
> 本节记录"把 `style` 自由文本进一步用 AI 标准化为提示词"的候选方案，作为后续迭代选项。

### 10.1 动机

预设枚举（5 个内置风格）+ 自由文本已覆盖大部分需求；但自由文本质量参差（如"暖暖的北欧 + 木质 + 绿植"这类组合描述），直接拼入 AI 生成质量不稳定。
- **AI 生成质量不稳定**：4 字用户输入远不如 50 字枚举 prompt 信息密度高
- **prompt 注入风险**：自由文本成为 AI 输入的一部分，可被恶意构造
- **数据库脏数据**：`style` 字段失去聚合统计价值

### 10.2 方案 E：AI 风格预优化

```
前端：用户输入自由文本 style
  ↓
ProjectService.create():
  1. styleLabel 命中已知 code → 走枚举 prompt
  2. style（自由文本）→ 调用 GLM-4-Flash 做预优化：
       System: "请把用户输入的装修风格描述标准化为 50 字以内的风格提示词，
                强调材质/色调/布局/光线，输出 JSON：{prompt: '...'}"
       User: <用户原文>
  3. 预优化结果落 t_design_project.custom_prompt
  4. §4.1 generate 时优先用 custom_prompt，否则用枚举 prompt + 原文
```

### 10.3 落地所需的工程改造

| 改造项 | 说明 |
|---|---|
| `AiPromptOptimizer` Service | 新建接口与实现，封装预优化 AI 调用 |
| GLM-4-Flash 调用配置 | 与 3D 生成（智谱 CogVideoX）区分，使用更便宜的文本模型 |
| Redis 缓存层 | 相同输入复用预优化结果，降低成本（key = hash(用户输入)） |
| 异步处理 | 预优化 2-5s，同步会卡请求；用线程池 + 任务状态机 |
| 注入防护 | 第一层 AI 仍可能被 prompt injection 绕过，需加关键词过滤 + 输出校验 |
| 失败回退 | AI 调用失败时降级为"用用户原文做基础 prompt"，保证可用 |
| 数据库 schema | `t_design_project` 加 `custom_prompt` 字段；`style` 存 `"custom"` 标记 |

### 10.4 权衡与决策

**当前阶段不实现的原因**：

1. 3D 生成主链路（§4.1）尚未完成，引入预优化会拖慢主流程
2. 预优化本身也是 AI 调用，**双倍 token 成本**对简历项目收益低
3. 第一层 AI 仍可被注入，**安全性提升有限**，只是把风险延后
4. 简历面试时能讲清"为何不放开自由输入 + 为何不做 AI 预优化"反而更显工程判断力

**后续触发条件**：

- 内置枚举扩展到 15-20 个后仍有用户反馈"找不到想要风格"
- 3D 生成主链路稳定运行后
- 有引入 Redis 的需求（其他模块也要用）

满足以上三点时，可按 §10.3 改造表逐步落地。

## 11. AI 设计助手接口 `/api/ai`（🚧 开发中）

> 需求（2026-09-18）：用户可与 AI 对话咨询装修问题，且 AI 具备**图文理解**能力（可发送装修图片提问）。
> 模型：智谱 **glm-4.6v-flash**（视觉多模态，OpenAI 兼容协议）；接入层：LangChain4j（starter 1.0.1-beta6，核心包 1.0.1）。
> 当前进度：**后端接口已完成并实测通过（2026-09-19，5 用例）**；纯文本多轮记忆已完成（2026-09-23），前端聊天页可用。
> 系统角色（`@SystemMessage`）：资深住宅装修设计师，仅回答装修相关问题，非相关问题礼貌拒绝。

### 11.1 AI 对话

`POST /api/ai/chat` （`Content-Type: application/json`，需鉴权）

**请求体** `AiChatRequest`：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `question` | string | 否 | 文本提问；纯图场景可空，后端补默认提问「请解释这张图」 |
| `images` | string[] | 否 | 图片列表，元素为 **DataURL**：`data:image/jpeg;base64,{base64数据}`；纯文本对话不传 |
| `conversationId` | string | 否 | **AI-3 新增**，仅纯文本链路使用：首轮不传，后端生成新会话；后续轮次原样带回实现上下文连续 |

> `question` 与 `images` **不可同时为空**，否则返回 400「输入不能为空」。

**请求示例**（图文混合）：

```json
{
  "question": "这张客厅效果图是什么装修风格？预算有限怎么复刻？",
  "images": [
    "data:image/jpeg;base64,/9j/4AAQSkZJRgABAQEASABIAAD..."
  ]
}
```

**响应** `data`：按链路分两种形态（AI-3 起）

- **纯文本链路**：对象 `{ conversationId, answer }`——`answer` 为回答文本；`conversationId` 为本次会话 id（首轮后端新生成，非首轮原样回传），前端保存并在后续轮次带回。
- **图文 / 纯图链路**：仍为 `String`（AI 回答文本），本期不接记忆。

纯文本响应示例：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "conversationId": "9f2c1a7e-...-...",
    "answer": "30 平原木风，建议橡木色地板搭配浅色布艺……"
  }
}
```

**分支行为**：

| 场景 | question | images | 行为 |
| --- | --- | --- | --- |
| 双空 | 空 | 空/缺省 | 400「输入不能为空」 |
| 纯文本 | 有 | 空/缺省 | 走文本对话 + 记忆读写，返回 `{conversationId, answer}` |
| 纯图 | 空 | 有 | 后端以「请解释这张图」作为默认提问，返回回答字符串（不走记忆） |
| 图文 | 有 | 有 | 文本 + 图片组装为同一条多模态消息发送，返回回答字符串（不走记忆） |

**错误场景**：

| 场景 | code | message |
| --- | --- | --- |
| question 与 images 同时为空 | 400 | 输入不能为空 |
| images 元素非合法 DataURL（无 `data:` 前缀或无逗号） | 400 | 图片格式错误，请上传 DataURL 格式的图片 |
| 模型限流（429）/ 超时 / 上游 5xx / 网络不可达 | 503 | 对不起，当前AI服务繁忙，请稍后再试~ |
| API Key 错误 / 欠费（401/403） | 原样透出模型错误 | 不转 503，便于排查配置问题 |

### 11.2 关键实现约定

1. **图片走 base64，不走 URL**：本地开发环境上传文件返回的是 `http://localhost:8080/...`，智谱云端服务器无法访问本机地址，传 URL 会导致模型下载图片失败；部署到公网后才可改用 URL 方式。
2. **MIME 类型从 DataURL 头部解析**（`data:image/png;base64,` → `image/png`），不写死 `image/jpeg`，兼容 PNG/WebP。
3. **不自行 Base64 解码为字节数组**：langchain4j OpenAI 适配器接收 base64 字符串 + mimeType（`ImageContent.from(base64, mimeType)`），由适配器在请求体内重新拼装。
4. **异常转译边界**：仅 `RateLimitException / TimeoutException / InternalServerException / UnresolvedModelServerException` 四类瞬时错误转 503；鉴权/欠费类错误保留原异常，避免伪装成"繁忙"掩盖配置问题。
5. **双链路架构（版本限制所致）**：核心包 1.0.1 的声明式 `@AiService` 不支持 `List<ImageContent>` 参数（≥2 参时强制每参数带文本类注解，且消息组装只取文本）。故**纯文本走 `AiChatAssistant`（@AiService）；图文/纯图在 Service 层注入自动装配的 `ChatModel`，手工组装 `SystemMessage + UserMessage.from(List<Content>)`（TextContent 在前、ImageContent 在后）调用**。系统提示词抽为 `AiChatAssistant.SYSTEM_PROMPT` 常量供两条链路复用。
6. **避坑**：`UserMessage.from(String name, List<Content>)` 的第一个参数是用户昵称而非文本，正文必须用 `TextContent` 放入 Content 列表；`Content` 类型导包选 `dev.langchain4j.data.message.Content`，不要选 `...openai.internal.chat.Content`（内部 DTO）；Starter 已自动装配唯一 `ChatModel`，不要再手写 @Bean（重复 bean 启动失败）。
7. ~~临时测试接口 `GET /api/chat`（`TestAiController`）~~ 已删除（仅纯文本可用，`@RequestParam List<ImageContent>` 无法绑定图片）。
8. **已知行为**：glm-4.6v-flash 对纯文本非装修问题的拒绝遵循不稳定（实测问编程问题仍作答），图片场景拒绝正常；强化系统提示词列入后续 TODO。

### 11.3 多轮对话记忆（✅ 已实现 2026-09-23，本期仅纯文本链路）

**核心机制**：大模型无状态，记忆 = 每轮把该会话历史重新拼入；滑动窗口只保留最近 10 条消息，超量自动淘汰最老消息（SystemMessage 独立保留、不占名额）。

**契约变更**：见 §11.1——请求新增 `conversationId`；纯文本响应由字符串变为 `{conversationId, answer}`。

**后端组件（LangChain4j 1.0.1，注意包路径与新版不同）**：

| 组件 | 全限定名 | 职责 |
| --- | --- | --- |
| `ChatMemoryProvider` | `dev.langchain4j.memory.chat.ChatMemoryProvider` | 按 memoryId 取/建 ChatMemory（函数式接口，仅 `get(Object)`） |
| `MessageWindowChatMemory` | `dev.langchain4j.memory.chat.MessageWindowChatMemory` | 滑动窗口记忆，`builder().id(id).maxMessages(10).build()` |
| `@MemoryId` | `dev.langchain4j.service.MemoryId` | 标注会话 id 参数 |
| `@UserMessage` | `dev.langchain4j.service.UserMessage` | 标注本轮用户提问参数 |

**装配方式（字节码已核实）**：

1. 配置类声明一个 `ChatMemoryProvider` Bean，内部用 `ConcurrentHashMap` 持有各会话记忆，`computeIfAbsent` 保证同一会话拿到同一记忆实例：

```java
Map<String, ChatMemory> memories = new ConcurrentHashMap<>();
return memoryId -> memories.computeIfAbsent((String) memoryId,
        id -> MessageWindowChatMemory.builder().id(id).maxMessages(10).build());
```

2. `@AiService` 注解通过 **bean 名称**挂接该 Provider：

```java
@AiService(chatMemoryProvider = "chatMemoryProvider")
public interface AiChatAssistant {
    // 记忆版：框架自动 取历史→拼问题→调模型→回写问答
    String chat(@MemoryId String conversationId, @UserMessage String question);
}
```

3. 首轮 `conversationId` 为空时由 Service 生成 UUID，响应返回；前端后续轮次带回。

**边界与权衡**：

| 场景 | 行为 |
| --- | --- |
| 首轮不带 conversationId | 后端新建会话并返回新 UUID，回答基于系统提示 |
| 同一会话追问指代上文的问题 | 框架拼入最近 10 条历史，AI 可引用上下文 |
| 不同 conversationId | Map 中不同记忆实例，上下文互不串扰 |
| 对话超过 10 条 | 最老消息被窗口淘汰，不再发送给模型 |
| 服务重启 | 内存 Map 清空，旧会话失效（本期已知行为，后续升级 Redis） |
| 图文 / 纯图链路 | 走裸 ChatModel，本期不接记忆，响应仍为字符串 |

**后续演进（不在本期）**：① 图文链路手工记忆（调模型前取 `memory.messages()` 拼入，调完 `memory.add(userMessage/aiMessage)` 回写）；② 存储升级 Redis（langchain4j-redis 的 `ChatMemoryStore`）实现持久化与多实例共享。
